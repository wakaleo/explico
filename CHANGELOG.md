# Changelog

## Unreleased

- **Added:** `diff` can tell you what happens to your own examples. `explico diff <old> <new> --out report.md --examples <dir>` (library: `Explico.diff(old, new, examples = ..., oldPolicyDir = ..., newPolicyDir = ...)`) evaluates the same fixtures against both versions with OPA and adds a **`## Behaviour on your examples`** section: per control, every fixture whose outcome changed, in the cards' own words (``standing order pre-approved by Treasury: ✅ allowed -> ❌ denied``), or ``<fixture>: still ❌ denied, message changed`` when only the produced message differs. "No example changed outcome." when none moved. Each change in the JSON gets `examples: [{fixture, old, new}]` (only when examples were given), and `DiffReport.exampleChanges` lists them. `--fail-on-example-changes` exits `5` (after writing the report) when any example changed outcome. With `--old-data`/`--new-data` each version is evaluated with its own data. The section also says what it covered (`Compared 5 of 6 controls present in both versions; not compared: ...`), so "No example changed outcome." is never claimed for controls that could not be compared (a function, several same-named rules whose messages cannot be attributed, a fixture only one version could evaluate); the gate fails rather than pass when nothing could be compared. Without `--examples` the report is byte-for-byte what it was.

- **Added:** `diff` can compare the reference data. `explico diff <old> <new> --out report.md --old-data <file|dir> --new-data <file|dir>` (library: `Explico.diff(old, new, dataOld = ..., dataNew = ...)`) looks at the `data.*` documents each control reads -- the ones the card's *Reference data* block shows -- in each version of the data. A control whose documents differ is **`LOGIC_CHANGED` even when its Rego is identical**, with one line per document: ``reference data changed: `data ▸ limits ▸ single approver minor`: `{"EUR":100000,...}` -> `{"EUR":1000,...}` `` (`absent` for a version in which the document does not exist), in the *What changed* list, under the control's section and in the JSON `details`. Before, halving a limit in the data file was reported as `UNCHANGED` and `--fail-on` exited 0. A document no control reads is never reported; the values are compared as JSON (key order and layout do not matter); no Rego rule is evaluated. Give both options or neither (one alone is exit `1`). Without them the report is byte-for-byte what it was. A control that was only `DOCS_CHANGED` and whose data also changed is reported as `LOGIC_CHANGED` and its documentation changes are not listed in that entry.

## 0.4.0

Documentation you can act on. explico now tells you, without opening `index.md`, what is suboptimal in your Rego and what to do about it: a findings block after the coverage line, a *Documentation quality* section that names each problem with a fix hint, and a configurable gate (`--require`). It also covers policy sets that declare no control ids (the entry points are listed), and fixes three rendering problems found on real decision-object policies. Read the **Changed** entry before upgrading: a render of a policy with unrendered conditions, plain comment blocks or id-less rules now prints more.

- **Changed (read this before upgrading):** `explico render` prints a `Documentation quality (see index.md):` block on stdout after the coverage line when there is something to report, and the index's *Documentation quality* section appears for more policies (comment blocks that never reach the documentation, conditions shown as source, rules with no control id, and -- with `--examples` -- controls no example matches or that return a raw object). The three older bullets (missing description, no framework, duplicate title) now end with a fix hint, and the framework hint names `custom.frameworks`. Exit codes, gates and every rendered card are unchanged; a policy with nothing to report prints exactly what it did. A script that parses stdout should read the first line (`Rendering coverage: ...`) and ignore the rest.
- **Added:** a *Documentation quality* finding for rules with no control id that no other rule uses -- the entry points (`deny`, `violation`, ...) of a policy set without ids, which none of the control-level checks cover: ``- **No control id (N):** [pkg.rule](...), ... — add custom.control-id ...`` and a line in the terminal summary. "Used" is decided from opa's own parse, so a use inside a comprehension, an `every`, a `with` or through an import counts; functions, constants and default-only rules are never listed. Advisory, not a gap; `--control-id-from` (with `--group-by-control`) clears it. On Trivy's Kubernetes checks it lists 171 entry points for 177 files, on Gatekeeper's general templates 30 for 30. In `explico.json` as `quality.noControlId`. Public model: `RuleGroup` gains `isReferenced`. Spec §14.68.
- **Added:** the quality findings are now visible where you work. `explico render` prints them on stdout after the coverage line (`Documentation quality (see index.md):` and one line per kind: `2 controls have no description`, `1 comment block is not published`, `3 conditions are shown as source`, ...), nothing for a policy with nothing to report; the library returns the same lines as `RenderedDocs.findings`. Advisory: exit codes and gates are unchanged. The three older index bullets (missing description, no framework, duplicate title) now end with what to do, like the newer ones. Spec §14.67.
- **Added:** a guide, *Policies that document well* (`docs/guides/policies-that-document-well.md`): what to do about each finding in the index -- put the explanation in METADATA, give each entry point a control id, declare a decision's verdict, how to read "shown as source" -- with two rewrites that keep a policy's meaning (a constant list indexed with `[_]` becomes `x in list`; `count([x | ...]) > 0` becomes `some x in ...`). Every pair on the page is checked on every build: it falls back as stated, the rewrite renders completely, and both give the same answer on the sample inputs, evaluated by `opa` (`GuideRewritesTest`).
- **Added:** the values explico could not render *inside* rendered conditions -- the card footer's "contains N unrendered values" -- now appear in the index: ``- **Values shown as source (N):**`` lists each distinct source text (most frequent first, 25 at most, then "and N more") with the cards and `file:row` places where it occurs, linked with `--source-url`, plus a line in the terminal summary. `explico.json` `quality.valuesShownAsSource` has the full list. On Trivy's Kubernetes checks: 195 occurrences of 83 distinct values. Advisory, not a gap. Moving a statement is not a logic change for `diff`. Public model: `Operand.Unrendered` gains `row`. Spec §14.71.
- **Added:** every condition shown as source now says WHERE: the *Shown as source* sub-bullets put the `file:row` where each unrendered statement starts in parentheses after its card (``[SA-1](sas.md#sa-1) (`sas.rego:14`)``; a whole `every` block or `else` chain starts at its first row, a grouped control lists the places of all its rules), and `explico.json` `quality.shownAsSource` gains `places` (`{rule, file, row}`). Moving a statement is not a logic change for `diff`. With `--source-url` each place (and each *Comments not published* block) is a link to that exact line, and the JSON places and comment blocks carry a `url`. Public model: `Condition.Unrendered` gains `row`. Spec §14.69, §14.70.
- **Added:** a *Documentation quality* finding that says WHY conditions are shown as source: ``- **Shown as source (2):**`` with one sub-bullet per reason (`every`, `else-chain`, `with-override`, `function-call`, `helper-assignment`, `partial-rule-reference`, `comprehension`, ...), how many conditions, the cards they are on and one factual sentence about what explico needs to render that construct. It explains and never prescribes a rewrite. Advisory, not a gap; counts conditions only (an unrendered operand carries no reason); in `explico.json` as `quality.shownAsSource`. A render of a policy with fallbacks gains this bullet. Spec §14.66.
- **Added:** a *Documentation quality* finding for comments that never reach the documentation: a run of two or more plain `#` comment lines (outside every rule, not part of a `# METADATA` block) is listed with its file, first row and length -- ``- **Comments not published (2):** `policies/a.rego:1` (3 lines), ...`` -- with the hint to move what readers need into a `description`. explico publishes METADATA only, so such text is silently dropped today. Advisory: not a gap (`--fail-on-gaps` is unchanged), and a licence header is reported too. In `explico.json` as `quality.unpublishedComments`. Public model: `PolicyPackage` gains `unpublishedComments` (new `CommentBlock`). Spec §14.65.
- **Added:** `render --require <properties>` (library: `Explico.render(..., required = ...)`) chooses what `--fail-on-gaps` fails on: any of `title`, `description`, `frameworks`, `fixture` (a control no worked example matches) and `verdict` (a control that returns an object but declares no `custom.verdict`). The default is `description` and `frameworks`, exactly as before; shared titles and requirement gaps always fail. `fixture` and `verdict` need `--examples` (refused otherwise, exit `1`), an unknown name or `--require` without `--fail-on-gaps` is a usage error. The rendered documents do not change; `explico.json` records the set as `quality.required`. Spec §14.64.
- **Added:** two documentation-quality findings that say what to do, shown in the index's *Documentation quality* section and in `explico.json` (`quality.noMatchingExample`, `quality.rawDecisionObject`) when example fixtures are given: **No matching example** (no fixture makes the control match -- "add a fixture that makes it match") and **Raw decision object** (the control returns an object and declares no `custom.verdict`, so its examples show raw JSON -- "declare custom.verdict ..."). Findings, not gaps: `--fail-on-gaps` is unchanged. Nothing changes without example fixtures. Spec §14.63.
- **Fixed:** `some x in object.get(input, "items", [])` -- the defensive way to read a list that may be absent -- was shown as source, with every later `x.field` left as raw text and the rule short of 100%. It is now rendered as an iteration, ``for some g in `items` (default `[]`)``, and the later uses read as the usual `items ▸ [each g] ▸ kind`. The key may be a plain field (`items`, `narGroups`) or a quoted one (`my-items`), the first argument a longer plain path (`object.get(input.request, "reviewers", [])`). Only an empty-array default is modelled; another default, a key that is not a string literal and `every x in object.get(...)` stay source. Public model: `Condition.SomeIn` gains `defaultValue`. Spec §14.62.
- **Fixed:** a function's card no longer lists "Worked examples" with "not matched" entries -- a function is not matched by an input. It has no such section and no `workedExamples` key in `explico.json`; the rules that call it keep theirs.
- **Fixed:** a string literal with a tab, line feed or carriage return (`trim(value, " \t\n\r")`) was printed with the raw characters, breaking the line it sat on. Control characters are now written as escapes (`\t`, `\n`, `\r`, any other as `\u00xx`) in every rendered literal and in the `path: value` bullets of a worked example; a backslash, a quote and non-ASCII letters are unchanged.

## 0.3.0

Rendering of the decision-object policies that were shown as source (`else` chains, object-valued rules), one page per multi-file control, and `diff` and the example generator catching up. Everything new is opt-in or additive; read the **Changed** entries (reserved `custom:` keys including `mask`, whose malformed form now stops the render; no "Effect of a match" on an `else` chain) and the **Fixed** entry (links inside a diff report) before upgrading.

- **Added:** `custom.mask: [paths]` keeps values out of the documentation. List the input paths (dotted keys inside the fixture input, `[]` for every element of an array: `subjectId`, `requester.email`, `people[].email`) and every worked example of that rule shows `***` instead: in the `path: value` bullets, in the produced messages, a declared verdict's reason, remediation labels, status and timing, the raw value and the fixture's name -- in the Markdown and in `explico.json` (and in generated examples). The real input is still evaluated, so verdicts stay true; a string is hidden wherever its text occurs, a number only as a whole token. Per rule. **Only values that are in the fixture input can be hidden**: a value the rule derives or reads from `data` is not. Editing the declaration is a documentation change in `diff`. Public model: `DeclaredProjection` gains `mask` and `maskProblem`. Spec §14.61.
- **Improved (found by the pre-release security review):** a `custom.mask` path that hides nothing in any example (a typo, the wrong case, a leading `input.`) now gets one stderr warning per path instead of silently letting the value through; a masked string is also hidden in its JSON-escaped form (`json.marshal`, `%q`) and object keys are scrubbed; mask paths may not contain `|`, a backtick or a line break. `diff` no longer lets a control id that reads like another rule's `package.rule` (`control-id: release.deny` next to an id-less `release.deny`) swallow one of them; with `--group-by-control` a control id that slugs to a Windows device name (`CON`, `NUL`, `COM1` ...) gets `controls/con-control.md`; and the exit-4 message of `diff` now says to pass `--group-by-control` if the shared id is deliberate.
- **Changed (read this if you use `mask:` under `custom:`):** `mask` is now a reserved `custom:` key, and unlike the other projections a malformed declaration is **not** ignored with a warning: the render stops (`IllegalArgumentException`; the CLI prints the rule and the problem and exits `1`, writing nothing), because ignoring it would show exactly the values it was written to hide. A plain note under that name (`mask: yes`) now stops the render; rename it to keep it as a note.


- **Added:** `else` chains are rendered. A chain whose every branch can be rendered is now shown as ordered situations -- "This rule is decided in order; the first matching situation wins", then `Situation 1`, `Situation 2 -- no earlier situation applies and ...`, each with a `*Then:*` value, and `Otherwise` for a bodiless final `else` -- instead of a source block. All-or-nothing: one unrenderable branch keeps the whole chain as source. Every branch's conditions count towards coverage, are hashed by `diff` in order (so a reordered or edited later branch is a logic change) and appear in `explico.json` as `elseBranches` on the body. Not rendered as a chain: one of several definitions of the same name. This changes the output of any policy that uses `else`. Public model: `RuleBody` gains `elseBranches` (a new `ElseBranch` class). Spec §14.52.
- **Added:** declared verdicts for object-valued rules. A rule that returns a decision object can say which fields are its verdict in `custom.verdict` (`outcome`: a boolean field, `reason`: an optional string field); its worked examples then read `✅ compliant` / `❌ not compliant` with the quoted reason instead of a JSON blob and "matched". explico reads only the declared names, is strict about types (an example that does not fit keeps its raw JSON), warns once on stderr about a wrongly-shaped declaration and ignores it, and carries the same facts in `explico.json` (`verdict` on the rule and on projected examples). Editing the declaration is a documentation change in `diff`. Opt-in: output is unchanged without it. Public model: `RuleMetadata` gains `projection` (new `DeclaredProjection`, `VerdictProjection`). Spec §14.53.
- **Added:** more declared projections for object-valued rules, next to `custom.verdict`: `custom.actions` (`at` an array, `label` inside each element) lists the remediation under each worked example (`*Remediation offered:*` with each declared label, or `*No remediation offered.*`), `custom.annotations` (`at` an array of strings) adds `· *status: ...*` to the summary line, and `custom.timing` (`dueBy`, `startBefore`) prints the declared instants verbatim as a `*Timing:*` line. Strict and independent per example: anything the value does not fully support is simply not shown (never a partial list, never coerced); a wrongly-shaped declaration is ignored with one stderr warning naming the key and the rule. In `explico.json` as `actions`/`annotations`/`timing` on the rule and `remediation`/`annotations`/`timing` on examples; editing a declaration is a documentation change in `diff`. Opt-in. Public model: `DeclaredProjection` gains `actions`, `annotations`, `timing` (new `ActionsProjection`, `AnnotationsProjection`, `TimingProjection`). Spec §14.54.
- **Added:** `render --control-id-from <regex>` (with `--control-id-template 'CTRL-{id}'`) derives a control id from each rule's source file name, for a corpus that names its controls by file: `ctrl_1123.rego` becomes `CTRL-1123`, with no METADATA to write. The regex has a named group `id` and is matched against the file's base name; METADATA's `control-id` always wins and only the id is derived, never a title. Opt-in (output is unchanged without it); `render` only, so `diff` does not take the options. A derived id is marked as derived (a line on its card naming the file, `controlIdDerived: true` in `explico.json`, a note in the index legend), because it is a mechanical reading of a file name and not an attested METADATA value. Library: `Explico.render(..., controlIdFrom, controlIdTemplate)`; public model: `RuleMetadata` gains `controlIdDerivedFrom`. A derived-id control has no description or framework, so the index's *Documentation quality* section (and `--fail-on-gaps`) lists it. Spec §14.55.
- **Added:** `render --group-by-control` gives every control id shared by two or more rules ONE page, `controls/<id>.md`, for a control split over several files and packages: each rule is a sub-section (its whole card, with its worked examples) in source-path order, package pages keep a short pointer instead of the cards, the index lists the control once (with its packages, rules and source files), and the documentation-quality findings count it as one control (missing a description or framework only if none of its rules has one). Links between cards follow the cards, relative to the page they are on; `explico.json` gains a `controls` array and `controlPage` on a grouped rule. Opt-in: output is unchanged without it. The returned `files` then include `controls/` keys, so a library caller writing them must create the directory (the CLI does). Library: `Explico.render(..., groupByControl)`. Works with `--control-id-from`. Spec §14.56.
- **Added:** `diff --group-by-control` (library: `Explico.diff(old, new, groupByControl = true)`) accepts a control id shared by several rules -- a control split over files -- instead of failing with exit 4. Each rule of a shared control is its own entry, identified by control id, package and rule (decided over both versions, so a control that gained or lost a sibling still matches its other rules): only the edited rule is `LOGIC_CHANGED`, a rule moved to another file is `UNCHANGED`, a rule renamed or moved to another package inside the control is removed and added. The report names the rule wherever it names a shared control (`SEC-28 — Sign-off (grp_signoff.signed_off)` in the bullets, card headings, JSON label and `--fail-on` message) and gives each card its own anchor. Without the option shared ids still exit 4. Spec §14.57.
- **Added:** `render --companion-url <template>` (with `--companion-label`, default `module`) adds a second link next to the source link, for a policy owned by a host-application module: `[module](https://host/modules/app.billing/src/billing/charge.rego#L8)`. The template takes `{file}`, `{line}` (as `--source-url`) and `{package}` (the Rego package, e.g. `app.billing`), at least one of `{file}`/`{package}`. It appears on each card's *defined in* line, on each package page's source files and as `companionUrl` in `explico.json`; not in the index. Opt-in: output is unchanged without it. Library: `Explico.render(..., companionUrl, companionLabel)`. Spec §14.58.
- **Improved:** `diff` names what changed in a rule with several situations. Where the "What changed" line used to say only "the rule's structure changed; see the source diff below" for a reordered `else` chain or a changed commentary string, it now says `situations reordered: now in the order of the old situations 2, 1, otherwise`, `situation 2: value changed from ... to ...` (or `otherwise: ...`, or `value changed from ... to ...` for a rule with one body), and `situation N removed (was: then ...)` / `situation N added (then ...)`, in the Markdown and in `explico diff --json` (`details`). Classification is unchanged. Spec §14.59.
- **Improved:** `--generate-examples` now models `count(<path>) <op> <whole number>` (a list of the length that makes the comparison true, or one short of it for a near-miss, up to 50 elements) and `time.parse_rfc3339_ns(<path>) <op> <path>` such as `input.now` (the other path is set to a fixed instant and the time to just before or after it), so rules written with those get a satisfying example and a near-miss. Every generated example is still verified by `opa eval` before it is shown; a count over `data.*`, contradicting counts and other constructs still get none. Spec §14.60.
- **Fixed:** in a diff report, a link from one card to a rule in ANOTHER package pointed at `<package>.md#...`, a page a diff report does not have; it is now a link within the report.
- **Changed (read this if your `custom:` uses these names):** `verdict`, `actions`, `annotations` and `timing` are now reserved `custom:` keys, because explico reads them (see the two entries above). A policy that used one of them as a plain note -- say `timing: quarterly` -- used to see it in the card's `*Custom:*` line; it now gets one warning on stderr (the value is not the mapping explico expects) and the key is no longer shown there. Rename such a key (for example `review-timing`) to keep showing it. Keys with any other name, and these four holding a valid mapping, are unaffected.
- **Changed:** no "Effect of a match" line on an `allow`/`deny` written as an `else` chain (it is always defined, so "a match" is ambiguous; its `*Then:*` lines say what each branch yields).

## 0.2.0

A new opt-in feature, and fixes for two defects found while building it. Recommended over 0.1.1, especially on Windows.

- **Added:** `every` blocks are rendered: `every x in coll { ... }` becomes a head bullet ("for every x in `coll`, all of the following are true (vacuously true when there are none)") with its conditions nested beneath it; the two-variable form and nested `every`s work too. All-or-nothing, like comprehensions: a collection that is not a plain path, or anything unrenderable inside, keeps the whole block as source. `kind: "every"` with nested `conditions` in `explico.json`. This changes the acceptance pack's own figures (the `every` helper is now 2 of 2; overall 24 of 24, 100%, was 22 of 23) -- a deliberate, approved amendment of the frozen acceptance README (spec §14.49). Note for library consumers: the public sealed `Condition` gains a variant (`Condition.Every`), so an exhaustive Kotlin `when` over it needs a new branch.
- **Improved:** real-world coverage (measured on Gatekeeper, Trivy, Regal and conftest): a declare-only `some i, j` and a bare `true` statement are no longer conditions; `import data.lib.pkg.fn` / `.rule` resolves a bare call or reference to that function or rule; a function's `msg := sprintf(...)` return is shown as its produced text. Gatekeeper 67% -> 81%, conftest 72% -> 79%. Spec §14.50.
- **Improved:** a free index variable (`pods[i]`, declared or not) is now understood: used once it is the wildcard `_` ("any of: ..."); used more than once it is introduced by a "for some index or key `i` of `pods`" bullet and every later use reads `[each i]`. `input[_]` no longer renders an empty breadcrumb. The public sealed `Condition` gains `SomeKey` (see the note on `Every`). Gatekeeper 81% -> 88%, conftest 79% -> 83%. Spec §14.51.
- **Note for `--fail-under` users:** rendering coverage is measured against what explico understands, so it can move on upgrade without any policy change (more constructs render; statements that test nothing stop counting). Pin the explico version in CI and re-baseline the threshold when you upgrade.
- **Fixed:** a worked example now lists a path that is only the argument of a call in a condition (`count(input.reviewers) < 2`): it is why the rule fired and used to be missing from the values shown.
- **Added:** `--generate-examples` (library: `Explico.render(..., generateExamples = true)`). explico derives worked examples itself from
  each rule's conditions where the author's own fixtures leave a gap: inputs that satisfy a rule body and "near-misses" that break exactly one
  condition, each **verified by `opa eval`** and shown in a separate, labelled *Generated examples* section with mechanical names. Off by
  default (output is byte-identical without it). Bodies it cannot model get none.
- **Added:** `render --source-url <template>` links every card's *defined in*, every package page's source files and every index row to the Rego line in your repository
  (`{file}` required, `{line}` optional; path segments percent-encoded). `sourceLine`/`sourceUrl` in `explico.json`. Pin a commit, not a branch.
- **Added:** CI gates, new exit code `5`: `render --fail-under <percent>` (rendering coverage), `render --fail-on-gaps` (documentation gaps: missing description or
  framework, shared titles, and with `--requirements` uncovered requirements or unlisted framework strings) and `diff --fail-on <categories>` (e.g. `LOGIC_CHANGED,REMOVED`).
  Output is still written; the reason is on stderr. Library: `RenderedDocs.gaps`, one worded line per gap.
- **Added:** a *Documentation quality* section in `index.md` (only when there is something to report) listing controls with no description, no framework or a
  title shared with another control; `render --requirements <file>` adds a *Requirements coverage* table -- which of your listed requirements have a control,
  which have **no control**, and which framework strings your controls use that are not on the list (a typo catcher). Both are also in `explico.json`.
- **Added:** machine-readable output. `render --json` writes `explico.json` (packages, rules, conditions with the exact card phrase or their verbatim
  source, coverage, metadata, effect of a match, every worked-example verdict, reference data); `diff --json <file>` writes the change report as JSON.
  Library: `render(..., json = true)` and `DiffReport.json`. Opt-in; the Markdown is byte-identical either way. Schema in `docs/json-output.md`.
- **Added:** every card for a rule named `deny`/`violation`/`allow` gains `**Effect of a match:** ❌ denied`/`✅ allowed`, stating the naming convention it
  rests on; no line for any other name. The index names every rule below 100% rendered with a link to its card, and the legend explains why a helper
  can show 0%. `explico --help` now describes each command.
- **Added:** a card now shows a rule's METADATA `authors`, `related_resources` and any other `custom:` key whose value is a scalar or a list of
  scalars (previously dropped), as `*Authors:*`, `*Related resources:*` and `*Custom:*` lines -- on a card, and on the package page for `scope: package` METADATA. Edits to them are `DOCS_CHANGED` in `explico diff`.
- **Added:** a `## What changed` section at the top of the diff report: one line per changed control --
  `removed`/`added`/`documentation changed: <fields>`/`logic changed`, the last with indented sub-bullets naming
  exactly which conditions, messages, body count, default outcome or fallback source changed -- so a reviewer
  doesn't have to read every full card to see what moved.
- **Added:** a *Reference data* section on a card that reads a plain `data.*` document (e.g. an exemption list): shows what the
  supplied data actually holds, resolved by `opa eval` and never a loaded rule's own value. Works with `--data` alone, with no
  `--examples` needed.
- **Added:** a policy digest -- a SHA-256 over the policy's `.rego` files (line endings normalised, examples/data/tool version excluded) --
  shown under the title of `index.md` and, shortened, at the end of every package document, so a reader can tell which policy version a
  document describes.
- **Added:** `index.md` titles link to their cards, and a *Controls by framework* table (built from METADATA `frameworks`) appears when any rule
  names one.
- **Changed:** the index column `Coverage` is now `Rendered` (it never measured control coverage), and a closing *How to read this index* section
  explains it. Every rendered document gains the digest footer line.
- **Added:** `RuleBody.messageArguments` (the plain input paths a message's `sprintf` reads) and `RenderedDocs.generatedExamples`.
- **Fixed (Windows):** worked examples failed for any policy directory given as an absolute path with a drive letter (`D:\policies`):
  `opa eval --data` treats everything before the first `:` as a document prefix, so `D:\a\x` was read as prefix `D` plus path `\a\x`.
  Such paths (and POSIX directories with a colon in their name) are now passed as `file://` URLs. Relative paths were never affected.
- **Fixed:** an `opa` failure reported on stdout (as `opa eval --format json` does) produced an exception with an empty message; it now
  carries opa's output, or at least the exit code.
- **Compatibility:** the public model grew (`RuleMetadata`, `PackageMetadata`, `RuleBody`, `RenderedDocs` gained fields). Their 0.1.x JVM constructors are kept
  (`@JvmOverloads`), so existing Java and already-compiled callers still link; `ModelBinaryCompatibilityTest` pins this against the 0.1.1 signatures.
  What does change is the generated data-class `copy(...)` signature (extra parameters), which affects only code that calls `copy()` on explico's model
  and was compiled against 0.1.x -- recompile it. The model is not binary-stable for `copy()`/destructuring before 1.0.
- **Changed:** failed tests now print their full assertion message in the Gradle/CI log (no effect on users).

## 0.1.1

Packaging corrections to 0.1.0. No rendering behaviour changes. **Use 0.1.1 instead of 0.1.0.**

- **Fixed:** 0.1.0's library jar (`explico-0.1.0.jar` on Maven Central) was the 6.6 MB runnable "fat" jar: it bundled
  Kotlin, kotlinx.serialization, Clikt and Mordant classes while the POM also declared them as dependencies, giving
  consumers duplicate classes on their classpath. The library jar is now ~390 KB with only `io.explico` classes; the
  runnable jar is a separate `explico-<version>-all.jar`, attached to the GitHub Release only.
- **Fixed:** `kotlinx-serialization-json` is now an `api` (compile-scope) dependency. `Fixture.input` exposes its
  `JsonObject`, but 0.1.0 declared it runtime-only, so a Gradle consumer could not compile against `Fixture`.
- **Changed:** bytecode now targets **Java 17** (was 21), compiled against the JDK 17 API surface; CI runs the runnable jar
  on a real JDK 17. Building from source still uses a JDK 21 toolchain.
- **Note:** because the library is now built with Kotlin 2.4, its POM declares `kotlin-stdlib:2.4.21`; a Gradle consumer on
  Kotlin 2.3 therefore resolves that stdlib version transitively (verified to build and run with the 2.3.0 compiler).
- **Added:** `SECURITY.md`, and a documented warning that rendering *with* worked examples executes the policy via
  `opa eval` (rendering without examples only parses).
- **Added:** the Apache `LICENSE` is included in the jars (`META-INF/LICENSE`).
- **Added:** a build-time test (`LibraryJarShapeTest`) that fails if the published library jar ever bundles third-party
  classes, contains a `Main-Class`, or grows past 2 MB.
- **Security (build and test tooling only; nothing that ships to users was affected):** AssertJ 3.27.3 -> 3.27.7
  (CVE-2026-24400, XXE in `isXmlEqualTo`, which no test uses) and the Kotlin Gradle plugin 2.3.0 -> 2.4.21
  (CVE-2026-53914, unsafe deserialization in the Kotlin build-cache metadata). All shipped runtime dependencies were scanned
  against OSV and are clean. The library is now built with Kotlin 2.4; consumers need Kotlin 2.3.0 or newer (unchanged).
- **Fixed (since 0.1.0 source, no separate release):** METADATA now attaches on Windows (opa reports backslash paths);
  CI runs on Linux, macOS and Windows.
