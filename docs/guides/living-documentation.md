# From Rego to living documentation

A policy file says what is enforced. It does not say what that *means* to the person who owns the control, and a document written once
goes stale the day the policy changes. explico closes that gap by treating your **policies** and a few **example inputs** as the source,
and regenerating the documents from them every time either changes. Because the worked examples are evaluated by real `opa eval`
on every run, the document does not just describe the rule: it shows what the rule does *today*.

This guide is the whole loop, with a real repository you can reproduce in a few minutes.

```text
policies/*.rego ──┐
examples/*.json ──┼──►  explico render  ──►  docs/policy-docs/*.md  ──►  review, CI, a published site
data/*.json     ──┘        (runs opa)
```

## 1. Lay out the repository

Three directories, all optional except the first:

```text
your-repo/
├── policies/            # your .rego files, any depth; METADATA on the rules you want documented
├── examples/            # worked-example fixtures, one JSON file per scenario
├── data/                # data.json your policies read through data.*, if any
└── docs/policy-docs/    # generated by explico; commit it
```

The repository used throughout this guide is explico's own sample set (`samples/policies`, `samples/examples`, `samples/data`).

## 2. Describe each control in METADATA

explico reads the standard OPA `# METADATA` block. The three things that make a rule into a documented control are a `title`, a
`description`, and `custom:` keys for its `control-id` and `frameworks`:

<!-- excerpt: samples/policies/approvals/change_approval.rego -->
```rego
# METADATA
# scope: document
# title: Production change approval
# description: |
#   Production deployments must reference an approved change ticket,
#   and the change author must not approve their own change.
# custom:
#   control-id: REL-001
#   frameworks:
#     - SOC 2 CC8.1
#     - ISO 27001 A.8.32
deny contains msg if {
	input.deployment.environment == "production"
	not input.change.ticket.approved
	msg := sprintf("release %v has no approved change ticket", [input.deployment.id])
}
```

The control id is also how `explico diff` recognises a control across versions, so renaming a rule does not look like a removal. The
full field-by-field walkthrough is in [Writing policies](../policy-authoring.md).

## 3. Add examples: one file per scenario

An example is an `input` document plus a name. explico evaluates it against **every** rule and shows the result on each card it touches.
Name the scenario, not the data:

<!-- excerpt: samples/examples/02-hotfix-without-change-ticket.json -->
```json
{
  "name": "hotfix without change ticket",
  "description": "An emergency production deployment attempted straight from a hotfix branch with no change ticket raised.",
  "input": {
    "deployment": { "id": "rel-1002", "environment": "production", "service": "payments-api", "timestamp": 1754060000 },
    "change": {
      "id": "chg-2002", "author": "asmith", "approver": "bjones",
      "approvals": [ { "user": "bjones", "role": "release-manager" } ]
    },
    "pipeline": {
      "stages": [ { "name": "build", "status": "passed" } ],
      "checks": [ { "name": "unit-tests", "status": "passed" } ]
    },
    "artifact": { "source_branch": "hotfix/urgent-fix", "labels": { "signed-off-by": "bjones" } }
  }
}
```

A good set has, for each control, at least one input that **triggers** it and one that **passes**. `index.md` has an *Example coverage*
column (`✓ / ✓` means both directions are shown, `✓ / –` means only one), so a thin set shows up as a visible gap instead of false
confidence. Where you have gaps, `--generate-examples` derives extra inputs from the rule's own conditions, each verified by `opa eval`
and clearly labelled as generated. See [Writing policies](../policy-authoring.md) for the fixture format, naming and where good examples come from.

## 4. Render and read

```sh
java -jar explico.jar render policies --out docs/policy-docs --examples examples --data data
```

The output directory is replaced on every run, so never put anything else in it. You get one document per Rego package plus an
`index.md` that lists every control, its coverage, and a framework-to-controls matrix. A card ends with the verdicts for your examples:

<!-- excerpt: docs/sample-output/release-approvals.md -->
```markdown
**Worked examples**

- **hotfix without change ticket** — ❌ denied *(Situation 1)*
  *"release rel-1002 has no approved change ticket"*
  - `deployment ▸ environment`: `"production"`
  - `change ▸ ticket ▸ approved`: absent
  - `change ▸ author`: `"asmith"`
  - `change ▸ approver`: `"bjones"`
```

Every verdict, message and situation label comes from OPA. explico lists the inputs the rule actually reads and their values, so a reader
sees *why*. See [Reading a card](../concepts/reading-a-card.md).

## 5. Commit the output, and regenerate it in CI

Commit `docs/policy-docs/`. Then have CI regenerate it and fail if anything differs:

```yaml
- name: Regenerate the policy documents and fail on drift
  run: |
    java -jar explico.jar render policies --out docs/policy-docs --examples examples --data data
    git diff --exit-code -- docs/policy-docs
```

The output is **byte-identical for identical inputs** (files, rules and fixtures are sorted; nothing depends on the clock), so a
difference always means a policy, an example, or the data changed without the document being refreshed. This single check is what makes
the documentation *living*: it can never be quietly out of date.

## 6. What a change looks like in review

Suppose a team decides hotfix branches may skip the change-ticket check, and adds one line to REL-001:

```diff
 	input.deployment.environment == "production"
 	not input.change.ticket.approved
+	not startswith(input.artifact.source_branch, "hotfix/")
```

Re-rendering (this is a real run on the sample set) changes the committed document. The new condition appears on the card, and the
example that used to be denied flips:

```diff
 - `deployment ▸ environment` is `"production"`
 - `change ▸ ticket ▸ approved` is absent or false
+- `artifact ▸ source branch` does not start with `"hotfix/"`
```

```diff
-- **hotfix without change ticket** — ❌ denied *(Situation 1)*
-  *"release rel-1002 has no approved change ticket"*
...
+- **hotfix without change ticket** — ✅ allowed
+  - `deployment ▸ environment`: `"production"`
+  - `change ▸ ticket ▸ approved`: absent
+  - `artifact ▸ source branch`: `"hotfix/urgent-fix"`
```

The reviewer does not have to trace the Rego in their head: the pull request shows, in plain words, that the policy is now more
permissive and exactly which scenario changed outcome. Two things to expect in such a diff: every package page's last line (the
*policy digest*) changes, because the digest covers the whole policy set; and an example that reads a newly referenced path gains a line
for it.

For a summary instead of a full diff, compare the two policy directories:

```sh
java -jar explico.jar diff old/policies policies --out policy-diff.md
```

```markdown
- [REL-001 — Production change approval](#rel-001) — logic changed
  - condition added: `artifact ▸ source branch` does not start with `"hotfix/"`
```

`--fail-on LOGIC_CHANGED,REMOVED` turns that into a gate. See [CI recipes](ci-recipes.md).

## 7. Publish it

The generated files are ordinary Markdown with working links, so you have three options, from least to most effort:

1. **Read it on GitHub or GitLab.** Committed Markdown renders there, and with `--source-url` every card links to the exact Rego line at
   that commit.
2. **Publish a site.** Any static-site generator that reads a folder of Markdown works. With MkDocs the whole configuration is:

    ```yaml
    # mkdocs.yml
    site_name: Release control documentation
    docs_dir: docs/policy-docs
    theme:
      name: material
    ```

    `mkdocs build --strict` builds the generated documents with their navigation and search, and fails on a broken link or anchor. (This
    is the configuration that was run against the sample set; it needs no changes to the generated files.) Deploy the result with GitHub
    Pages from the same workflow that regenerates the documents.
3. **Feed other tools.** Add `--json` for a machine-readable result of every rule, condition, verdict and coverage figure, for
   dashboards and GRC tools. See [JSON output](../json-output.md).

## 8. What the examples do and do not prove

Be clear about this with your auditors:

- **Examples are evaluated, not asserted.** A fixture has no "expected verdict". The card shows what the policy *does* with it, and a
  flipped outcome is visible in the diff (step 6) and fails the drift check (step 5), but explico does not tell you the new outcome is
  wrong. Review the diff.
- **METADATA is human-attested.** The title, description and frameworks are what the author wrote; explico cannot verify them. The
  checks `--fail-on-gaps` and `--requirements` make sure they are *present* and cover your listed requirements.
- **Coverage is about rendering, not about the control.** A rule shown as source is flagged and counted. See [Coverage](../concepts/coverage.md).

## Checklist

- [ ] Each control has a `title`, `description`, `control-id` and `frameworks` in METADATA.
- [ ] Each control has at least one triggering and one passing example (the *Example coverage* column shows `✓ / ✓`).
- [ ] The generated documents are committed, and CI regenerates them and fails on drift.
- [ ] Pull requests that change policies show the document diff, and `explico diff --fail-on` flags logic changes for review.
- [ ] The explico and `opa` versions are pinned in CI, so a coverage figure or a phrase cannot change under you.
