# Limits and FAQ

## What explico deliberately does not do

- **No LLM, no guessing.** Nothing in the output is generated by a model or inferred. See [True by construction](concepts/true-by-construction.md).
- **No Rego parser of its own.** Parsing, annotations and evaluation all go through the real `opa` binary, so explico cannot drift from what OPA does.
- **No HTML output or server.** Markdown, plus opt-in [JSON](json-output.md) for other tools.
- **No inlining of helper rules.** A reference to another rule is a link to its card, not a copy of its body.
- **No git integration.** `explico diff` takes two directories; check out the versions yourself (for example with `git worktree`).
- **No decision-flip analysis across versions.** `diff` reports structural change; it does not evaluate old and new on the same inputs.

## What it shows as source

These are rendered as a marked, verbatim-source block, never as prose: a `with` override, an `else` chain (its branches are tried in
order, which a list of situations would misstate), and a comprehension or `every` block that contains anything explico cannot render.
The [Rego coverage reference](rego-coverage.md) lists every construct and builtin, what it does today and why.

## Frequently asked questions

**Does it run my policy?**
Only to build worked examples. `render` without `--examples` parses the policy and reads its annotations; with `--examples` (or
`--generate-examples`) it runs `opa eval` on the fixtures. Nothing else evaluates anything.

**Does it send my policy anywhere?**
No. explico makes no network calls, with one exception: `explico demo --fetch-opa` downloads a pinned, checksum-verified `opa` binary
from its GitHub release if you ask it to.

**Which `opa` version?**
OPA 1.x on `PATH` (or `OPA_BIN`). It is developed and tested against 1.19.0, which CI pins. A different 1.x should work but is not guaranteed
byte for byte.

**Can it read Rego v0 (`deny[msg] { ... }`)?**
Yes: pass `--rego-version v0`. It is always chosen explicitly and never auto-detected. The Gatekeeper library renders this way.

**Why does my card say `absent` in a worked example?**
The fixture has no value at that path. That is often exactly the point of a fixture ("hotfix without change ticket").

**Why is my rule at 0%?**
Its conditions are constructs explico shows as source. Open the card: each ⚠ block is the verbatim Rego. Rank what is costing you coverage
with the `reason` fields in the [JSON output](json-output.md).

**Can I trust the description and frameworks on a card?**
They are exactly what the policy's METADATA says. explico shows them faithfully but cannot verify them. `render --requirements`
and `--fail-on-gaps` check that controls are documented and cover your listed requirements, not that the text is right.

**What does `any of:` mean?**
The path has a wildcard (`pods[_]`, or an index variable used once): the condition holds if **at least one** element satisfies it.

**Why did my coverage change after upgrading?**
A release can render more constructs, or stop counting statements that test nothing. See [Coverage](concepts/coverage.md).

**Is the output stable?**
Yes. The same policy directories give byte-identical output: files, rules, fixtures and map keys are all sorted, and nothing depends on
the clock.
